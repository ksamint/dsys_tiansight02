# Consolidation plan · one slide library, one export path

Status: plan for autonomous execution by an agent. Written 2026-10-21 against PR #3
(`claude/approved-runtime-2026-10-21`, head `3bd4d2d`). No human checkpoint until the
production review at the end (§10). Every phase ends in automated acceptance the agent runs
itself. If a step cannot be completed as written, take the documented fallback, record it in
`docs/consolidation-log.md`, and continue. Do not ask questions; do not stop early.

## 0. Principles (owner-confirmed 2026-10-21)

1. **One source per slide.** A slide exists once, keyed by its permanent UUID, in the slide
   library. Decks are ordered lists of slide references. A deck that needs a slide from another
   deck references it; it never copies or rebuilds it. Case studies in particular live in one
   place and are referenced by the corporate intro, the sales deck and the exhibit deck. The
   owner's registry already shares five UUIDs (four profiles, 联系) across all three decks;
   this plan generalises that rule to every slide.
2. **The corporate intro is always current** because it is the deck that references the
   canonical slides, and every other deck references the same records. A change to a shared
   slide marks every deck that uses it stale; decks are rebuilt by command, never by hand.
3. **The repository is the content API.** A later web app with MCP functions reads three
   contract files at a tagged release and calls one build command (§8). Rendering stays in this
   repository so the web app, an agent and CI produce identical output.
4. **The design system stays neat.** Five working folders, one copy of every visual asset, an
   asset register with approval provenance, and historical material in `archive/` only.

Non-negotiables carried over from `AGENTS.md`: foundation authority of `brand/`, no raw
colours outside `tokens.css`, serif only, no CDN or remote resources, no emoji, nothing
sensitive in this public repository, copy quoted verbatim from `guidelines/company-intro-v3.md`
and existing sources, never invented or paraphrased.

## 3. Phase A · slide library

### 3.1 Slide record schema (`content/slides/<uuid>.json`)

```json
{
  "id": "ed451b90-…",
  "label": "联合创始人 · 边江",
  "owner": "intro",
  "component": "ProfileSlide",
  "props": { "person": { "$team": "边江" } },
  "publish": "web",
  "cat": "team",
  "type": "profile",
  "tags": ["团队"],
  "purpose": "边江个人介绍：履历、服务品牌与代表成果。",
  "status": "maintained"
}
```

- `id`, `label`, `cat`, `type`, `tags`, `publish`, `purpose`, `evidence`, `note` are copied
  verbatim from the owner's registry (`content/slide-catalog.js`). IDs never change.
- `owner` is the deck whose topic the slide belongs to: `intro`, `exhibit`, `kitchen`, `sales`.
  Shared slides (profiles, 联系, 团队, cases, 伙伴背书) are owned by `intro`.
- `component` is a name exported by the pinned runtime (`manifest.json.components`) or
  `ext:<Name>` from a deck extension (§3.5).
- `props` are the exact props the component receives, after reference resolution (§3.4).
- `status` is `maintained` (props present, builds) or `planned` (registry entry only, no
  props). Planned slides are never built and never invented.

| Slides | Source of props | Notes |
|---|---|---|
| 47 corporate pages | `docs/claude-design-system/templates/company-intro/CompanyIntro.dc.js` (already on the e0a760 runtime, rendered by the runtime test) cross-checked against `deliverables/company-intro-v3/gen/vals.json` | Where the two differ, `vals.json` wording wins (it is the generator that produced the approved PDF); record every difference in the log. |
| 5 sales pages in the intro registry (四个阶段, 服务模式, 样张为证, 图谱, 伙伴案例) | `templates/sales-deck/SalesDeck.dc.html` and `slides/index.html` | Pin defaults: `active` 1, `highlight` 1, `figure` `"scatter"`, `sample` true. |
| 41 exhibit pages | `deliverables/exhibit-design/src/TiansightDeck-Exhibit.dc.html` | Extract the props the `S()/scr()/mtx()` helpers produce; keep the text-wrapping helpers (`nb`, `KT`) as a build-time transform declared in the deck manifest, not in the data. |
| 14 sales-deck pages | `templates/sales-deck/SalesDeck.dc.html` | Mint IDs with `uuid5(NAMESPACE_URL, "tiansight:sales:<label>")`. Reuse intro IDs for 创始团队, 伙伴背书, 联系, 伙伴案例. |

Five registry entries already carry the same UUID in all three decks. Those become one file each.
Expected count after Phase A: 135 unique slides (52 + 52 + 41 − 10 shared), plus the sales
deck's non-shared pages.

### 3.3 Case studies (`content/cases/<id>.json`)

One record per customer. Fields: `id` (`case-01` … `case-08`), `name` (verbatim from the named
customer list), `summary` (the intro's case slide props), `gallery` (the exhibit's photos and
captions where they exist, today only 游园京梦), `assets` (registered asset paths), `approval`
(reference to the owner approval in `assets/index.json`). Case slides in any deck carry
`props: { "$case": "case-06" }` plus layout-only props. The gate fails on any slide that
defines a case name inline.

### 3.4 Reference resolution

`{"$team": "<name>"}` → the person record from `content/team.json`;
`{"$contact": true}` → `content/contact.json`; `{"$case": "<id>"}` → `content/cases/<id>.json`;
`{"$partners": true}` → `content/partners.json`; `{"$asset": "<path>"}` → a registered asset
path, resolved relative to the built HTML. Resolution is one pass, no nesting beyond one level,
implemented once in `scripts/content_lib.py` and used by every builder.

### 3.5 Extensions

The exhibit source defines `PhotoPoints` and `zoneChart` inline. Move them unchanged into
`content/extensions/exhibit.js`, registered on `window.TIANSIGHT_EXT.exhibit`. Slides reference
them as `ext:PhotoPoints`. Extensions use only runtime exports and tokens; the gate's raw-colour
and font checks run on them.

### 3.6 Acceptance for Phase A

- `python3 scripts/content_lib.py --check` passes: every file parses, IDs unique across the
  library, every `$ref` resolves, every `component` exists in the runtime manifest or an
  extension, `planned` slides have no props, `maintained` slides have props.
- A migration test renders each maintained slide's resolved props through the runtime (reuse
  `scripts/test_component_runtime.mjs` machinery) with zero runtime errors.
- For the 47 corporate slides and 41 exhibit slides, the rendered text of each slide equals
  the text rendered by the pre-migration source (normalise whitespace and U+2060). Any diff
  is a migration error; fix the migration, never the copy.

## 4. Phase B · deck manifests (`content/decks/<id>.json`)

```json
{
  "id": "intro",
  "title": "侍天 TIANSIGHT 企业介绍",
  "canonicalSource": "guidelines/company-intro-v3.md",
  "slides": ["b63a770d-…", { "id": "…", "overrides": { "page": 5 } }],
  "params": { "date": { "default": "2026-10", "editor": "text" } },
  "profiles": {
    "internal": { "publish": ["web", "banner", "internal"] },
    "client":   { "publish": ["web", "banner"] },
    "web":      { "publish": ["web"] }
  },
  "transforms": ["keep-words"],
  "status": "maintained"
}
```

- Decks: `intro` (the 52 registry UUIDs, in registry order), `exhibit` (41), `sales` (14),
  `kitchen` (52, `status: planned`, builds nothing, listed in the catalog as planned).
- A manifest may only reference library IDs. Overrides are layout-only (page number, `active`,
  `highlight`, `figure`); the gate rejects overrides that carry copy fields (`title`, `body`,
  `name`, `quote`, and any string longer than 24 characters).
- Page numbers are assigned at build time per profile, never stored in slides.
- Delete `content/slide-catalog.js` after `content/deck-catalog.json` is generated from the
  manifests (§6); the registry's data now lives in the slide files.

Acceptance: `python3 scripts/build_deck.py --all --check` (§7) passes; the `intro` client
profile has 47 pages (the 5 internal and sales-internal pages excluded) — verify the exact
count from the `publish` flags and record it.

## 6. Phase D · catalog and versions

`node scripts/build_deck_catalog.mjs` regenerates `content/deck-catalog.json` from manifests
and slides:

```json
{
  "schema": "tiansight.deck-catalog/2",
  "runtime": "2026.10.21-e0a760",
  "decks": [{
    "id": "intro", "title": "…", "status": "maintained",
    "contentVersion": "<sha256 of resolved slides + referenced asset hashes>",
    "systemVersion": "2026.10.21-e0a760",
    "profiles": ["internal", "client", "web"],
    "slides": [{ "id": "…", "order": 1, "label": "…", "publish": "web", "owner": "intro" }],
    "latestBuilt": { "contentVersion": "…", "systemVersion": "…", "builtAt": "…", "path": "build/intro/" },
    "latestApproved": null
  }]
}
```

- `latestBuilt` is set automatically by `scripts/release.py <deck>` (§7). `latestApproved` is
  set only at the production review (§10). The web app reads `latestApproved` in production and
  `latestBuilt` in staging. This replaces PR #3's `latestApprovedBuilt`.
- `contentVersion` changes when any referenced slide, case, person, contact, partner or asset
  changes, so a shared-slide edit marks every deck that uses it stale.
- `dist/components/current.json` keeps `supported`; drop `latestApprovedBuilt` from it (deck
  approval lives in the catalog, runtime approval is the `supported` pointer).

## 7. Phase E · one build path

`python3 scripts/build_deck.py <deckId> [--profile client] [--param date=2026-11] [--pdf] [--check] [--all]`

1. Resolve the manifest and slides (§3.4), apply the profile filter, assign page numbers,
   apply transforms.
2. Emit `build/<deck>/<profile>/index.html`: the same head as PR #3's `build_exhibit.py`
   (pinned runtime scripts, `deck-stage.js`, extensions, `<h1 class="sr-only">`, `<main>`),
   one `<section data-slide-id data-label>` per slide, and a small boot script that mounts
   `React.createElement(NS[component], props)` into each section from an inline JSON blob.
   This replaces the DC `support.js` templating for built decks; the runtime's `support.js`
   stays in `dist/` for the specimen cards only.
3. Write `build.json` with `deckId`, `profile`, `contentVersion`, `systemVersion`, `htmlSha256`,
   `params`, `builtAt` (ISO date, from the commit date for reproducibility).
4. `--pdf` runs `node scripts/export_pdf.mjs build/<deck>/<profile>/index.html`, which is the
   PDF part of `test_component_runtime.mjs` generalised: title carries `contentVersion` and
   `systemVersion`; 1280×720 at 960×540 points; fonts embedded; `printBackground`.
5. `uv run --with pillow --with pymupdf python scripts/verify_pdf.py <deck> <profile>` writes
   `verification.json`: page count, per-page text equality with the HTML, clipped words, mean
   pixel difference against the HTML screenshots (< 12/255), fonts embedded, and the PDF's
   byte hash for provenance.
6. `--check` rebuilds HTML and `build.json` in memory and compares; PDFs are compared by the
   versions in their metadata title and in `verification.json`, **not** by byte hash
   (Chromium output is not byte-stable; PR #3's hash gate fails on every rebuild).

`scripts/release.py <deck>` = build all profiles with `--pdf`, verify, update `latestBuilt`
in the catalog, and write `build/<deck>/RELEASE.md` (versions, page counts, verification
summary). Commit PDFs only for `latestBuilt` of each deck and profile, replaced in place.

Retire after the manifests reproduce them: `scripts/build_exhibit.py`,
`scripts/verify_exhibit_pdf.py`, `templates/sales-deck/` (keep `deck-stage.js` in `dist/`),
`deliverables/exhibit-design/`, `deliverables/company-intro-v3/` (generator, inline-style
slides, stale PDF), `docs/claude-design-system/templates/`. Their content is in the library.

Acceptance: `python3 scripts/release.py intro && … exhibit && … sales` succeeds offline;
`build_deck.py --all --check` passes; `test_component_runtime.mjs` is updated to inspect
`build/*/internal/index.html` instead of the retired paths, and still renders all 33 cards and
three UI pages with zero errors and zero external requests.

## 8. Contract for the web app and MCP (read-only, this PR only documents it)

## 12. Agent rules while executing

- Never invent, paraphrase or "improve" copy. Verbatim moves only. If a required string is
  missing from every source, leave the slide `planned` and log it.
- Never add a hex colour, a font family, a remote URL or an emoji anywhere.
- Never push data from the sensitive list in `docs/maintaining.md` §6. Read every diff.
- Commit at the end of each phase with the phase name in the subject. Push the branch after
  each commit so progress is visible.
- When a documented path is impossible (missing tool, runtime component that cannot take the
  extracted props), implement the nearest fallback that keeps the principle in §0 intact,
  log it, and continue. Do not widen scope into the report kit, the website or the brand layer.
- Do not merge, deploy, tag or set `latestApproved`. Those belong to the production review.
